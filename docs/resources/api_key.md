# mistral_api_key (Resource)

Manages a workspace API key created for a user of the organization, with the Admin API key (`admin_api_key`). The Admin API needs an Enterprise plan and access granted by Mistral. The key acts in its workspace, with the quota, limits and resources of that workspace.

-> **Public preview at Mistral.** The Admin API is in public preview: Mistral can change its fields without a deprecation period, and following them may take a new release of the provider.

~> **Not verified against the live API.** This resource is tested against a fake of the Mistral API written from Mistral's documentation. No acceptance test has run against a Mistral organization yet: please report any difference with the live API in an issue.

## The secret

Mistral returns the secret of a key once, when it creates the key. The provider stores it in the state, in the sensitive `key` attribute: protect the state as you protect the key. An import cannot recover the secret, so `key` is null after an import.

A key created in a configuration cannot configure a `mistral` provider block of that same configuration, since a provider argument must be known at plan time. Hand it to a secret store, or to another configuration.

## No update

The API cannot change a key. Changing `workspace_id`, `user_id`, `name` or `expiration` replaces the key: Terraform deletes the old key, whose applications lose access, then creates a new key with a new secret. With `create_before_destroy`, the new key exists before the old one goes. Destroying the resource deletes the key at Mistral.

## Expiration

When an expiration policy applies to the workspace, Mistral creates a key asked without an expiration date, or with a date beyond the maximum, "with the latest expiration date allowed by the policy". `expiration` keeps the date of the configuration, and `expiration_date` gives the date Mistral set: a shortened date does not plan a replacement.

An expired key stays in the state for as long as Mistral lists it. To renew it, change `expiration`, which replaces the key. Adding `expiration` to a key created without one replaces it too, since the API cannot set an expiry on an existing key, unless the key is still valid and already expires on that very date: an `expiration_date` after today (UTC), as a policy may have set it, equal to `expiration`. The apply then records the date in place, and the key keeps its secret. Any other date, earlier or later, replaces the key, and so does a key that never expires, expires today or has expired: under a policy, a new key may get another date than the old one, and the plan shows the replacement. Today is read when Terraform plans, and again when it applies: if an apply runs after midnight UTC on the day its plan's key expires, Terraform stops it with "Provider produced inconsistent final plan" and changes nothing. Run plan and apply again.

The Admin Panel also sets a connector access scope on a key. The API does not take one, and the documentation does not say which scope a key created through the API gets.

## Example Usage

```terraform
variable "service_user_id" {
  description = "The ID of the user the key is created for."
  type        = string
}

data "mistral_workspace" "production" {
  name = "Production"
}

# The secret is in mistral_api_key.backend.key, and in the state: hand it to
# a secret store rather than to an output.
resource "mistral_api_key" "backend" {
  workspace_id = data.mistral_workspace.production.id
  user_id      = var.service_user_id
  name         = "prod-backend"
  expiration   = "2027-06-30"
}

output "backend_key_expires_on" {
  description = "The date the key expires, which an expiration policy can set earlier than requested."
  value       = mistral_api_key.backend.expiration_date
}
```

## Schema

### Required

- `user_id` (String) The ID of the user the key is created for. Changing it replaces the key, except after an import, where the first apply records it in place.
- `workspace_id` (String) The ID of the workspace the key acts in, whose quota, limits and resources it uses. Changing it replaces the key.

### Optional

- `expiration` (String) The date the key should expire, in RFC 3339 date format (`2027-06-30`). When null, the key never expires, unless an expiration policy applies. The state keeps the configured date: `expiration_date` gives the date Mistral set. Changing it replaces the key, except when it is added to a key that has none in the state, as after its create without one or after an import, and whose `expiration_date` is after today (UTC) and the same date: the apply then records it in place.
- `name` (String) The name of the key, of at most 255 characters. Changing it replaces the key.

### Read-Only

- `created_at` (String) When the key was created, in RFC 3339 format.
- `expiration_date` (String) The date the key expires, as Mistral set it: `expiration`, or an earlier date when an expiration policy applies to the workspace. Null when the key never expires.
- `hidden_key` (String) The masked secret, as the Admin Panel shows it.
- `id` (String) The API key ID, a UUID.
- `key` (String, Sensitive) The secret of the key, which only the create returns. The state holds it; it is null after an import.

## Import

The import reads the key without its secret: `key` stays null. The API does not return `user_id`, and the provider never reads `expiration` back, so both are null after an import. The first apply records `user_id` in place. It records `expiration` in place under the rule of *Expiration* for a date added to a key: when the imported key's `expiration_date` is after today (UTC) and the same date. Otherwise, as for a key that never expires, the plan replaces the key, and its applications lose access. This includes a key Terraform created with an `expiration` that an organization policy shortened: re-imported with the same configuration, its `expiration_date` is earlier than `expiration`, so the plan replaces it. To import a key without replacing it, leave `expiration` out, or, when its `expiration_date` is after today, set `expiration` to that date in the `YYYY-MM-DD` format: its date in UTC if the API gives a date and time, since `expiration` takes a date only.

In Terraform and OpenTofu 1.12 and later, an `import` block can use the resource identity:

```terraform
import {
  to = mistral_api_key.backend
  identity = {
    id = "5a6b7c8d-9e0f-4a1b-8c2d-3e4f5a6b7c8d"
  }
}
```
