# mistral_workspace_member (Resource)

Makes a user of the organization a member of a workspace, with workspace roles, with the Admin API key (`admin_api_key`). The Admin API needs an Enterprise plan and access granted by Mistral.

-> **Public preview at Mistral.** The Admin API is in public preview: Mistral can change its fields without a deprecation period, and following them may take a new release of the provider.

~> **Not verified against the live API.** This resource is tested against a fake of the Mistral API written from Mistral's documentation. No acceptance test has run against a Mistral organization yet: please report any difference with the live API in an issue.

## Roles

`role_names` takes the workspace role names of the Admin API, such as `user` (Vibe), `dev` (Studio), `workspace_contributor` (both, and Mistral Code) or `workspace_admin`. A user's roles add up. Without `role_names`, the user gets `workspace_contributor`, the role Mistral gives a new member.

Mistral reads the roles of a member back as role UUIDs, which the provider names with `GET /v1/admin/roles`; the Mistral documentation says that this list needs role-based access control (RBAC) enabled for the organization. A role that this list does not name shows in the plan as it is, and the next apply sets the configured roles.

## Existing members

The API adds a member and changes their roles with the same call. To avoid taking over a membership made outside Terraform, the create fails when the user is already a member of the workspace, and gives the `import` block that brings the membership under Terraform. This is the case of the `admin_user_id` of a `mistral_workspace`, and of every member after `add_all_org_members`.

Organization admins have access to every workspace without being members of it.

## Destroy

Destroying the resource removes the user from the workspace and deletes their permissions in it. The user stays a member of the organization.

A user removed from the organization is no longer a member of any workspace: the resource leaves the state, and the next apply tries to add the user again, which fails.

## Example Usage

```terraform
variable "ada_user_id" {
  description = "The ID of a user of the organization."
  type        = string
}

data "mistral_workspace" "ml" {
  name = "ML Research"
}

resource "mistral_workspace_member" "ada" {
  workspace_id = data.mistral_workspace.ml.id
  user_id      = var.ada_user_id
  role_names   = ["dev", "observability_viewer"]
}
```

## Schema

### Required

- `user_id` (String) The ID of the user, a member of the organization. Changing it replaces the membership.
- `workspace_id` (String) The ID of the workspace. Changing it replaces the membership.

### Optional

- `role_names` (Set of String) The workspace roles of the user, whose permissions add up, such as `user`, `dev`, `mistral_code_user`, `billing`, `workspace_contributor`, `workspace_admin` or `observability_viewer`. Defaults to `["workspace_contributor"]`, the role Mistral gives a new member. `GET /v1/admin/roles` lists the roles of the organization.

### Read-Only

- `id` (String) `<workspace_id>:<user_id>`.

## Import

In Terraform 1.12 and later, an `import` block can use the resource identity:

```terraform
import {
  to = mistral_workspace_member.ada
  identity = {
    workspace_id = "8f3c2a1e-5b7d-4c9e-a0f1-2b3c4d5e6f70"
    user_id      = "1d2e3f4a-5b6c-4d7e-8f9a-0b1c2d3e4f5a"
  }
}
```
