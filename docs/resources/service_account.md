# mistral_service_account (Resource)

Manages a service account of a workspace, with the standard API key (`api_key`): a non-human identity that a workload, such as a workflow worker, uses to authenticate to Mistral, and the workspace roles it holds. See [Service accounts](https://docs.mistral.ai/admin/identity-access/service-accounts).

-> **Public preview at Mistral.** The Service Accounts API is in public preview: Mistral can change its fields without a deprecation period, and following them may take a new release of the provider.

~> **Not verified against the live API.** This resource is tested against a fake of the Mistral API written from Mistral's documentation. No acceptance test has run against a Mistral organization yet: please report any difference with the live API in an issue.

## Workspace

A service account belongs to one workspace and cannot move to another. The API takes the workspace in `workspace_id`, while a standard API key acts in the workspace it was created in: set `workspace_id` to the workspace of the provider's key, and manage the service accounts of several workspaces with one aliased provider block per workspace. Whether the API refuses the ID of another workspace is not verified. The owner of the key needs the Workspace admin role (`workspace_admin`) on the workspace.

## Name

The name is unique in the workspace and cannot change. It is a lowercase letter followed by lowercase letters, digits or hyphens, 2 to 63 characters. The API lowercases a mixed-case name, so the provider refuses one rather than plan a replacement on every run.

Changing `name` or `workspace_id` replaces the service account, and deleting a service account deletes its credentials: every workload using them stops authenticating until it gets new ones.

When the workspace already has a service account by that name, the create fails and points to an `import` block. A create that failed on a server error may still have made the account: the next apply then fails on the name, and the import brings the account under Terraform. The status the API answers for a name that is taken is not documented.

## Roles

`role_ids` holds the IDs of the workspace roles of the service account: get them from the `mistral_assignable_service_account_roles` data source. A workflow worker needs the `workflow_executor` role (see [Roles and permissions](https://docs.mistral.ai/admin/identity-access/roles-permissions)).

The create sends the roles with the account. A change sends them in one call that replaces them as a whole: a role left out of `role_ids` is revoked. The API requires one role at least; the `member` role grants no permission, although workspace-wide sharing may still grant access. A role granted in the Admin Console shows as drift, and the next apply revokes it.

## Credentials

The API manages the identity and its roles, not its credentials. The API keys and the workload identity credentials of a service account are added in the Admin Console only: open the service account and click **Add new authentication**.

- An **API key** of a service account is shown once, when it is created. It is scoped to the workspace of the service account and acts with its roles.
- A **workload identity credential** lets a workload, such as a pod of a Kubernetes cluster that an organization admin registered as a trusted issuer, authenticate with a short-lived token the cluster signs, with no stored secret. See [Workload identity federation](https://docs.mistral.ai/admin/identity-access/workload-identity).

Destroying or replacing the resource deletes the service account and its credentials.

## Example Usage

```terraform
# The workspace of the provider's API key.
locals {
  workspace_id = "5d3c4c7e-1f0a-4b8e-9c61-0a6f3e2b9d10"
}

data "mistral_assignable_service_account_roles" "this" {
  workspace_id = local.workspace_id
}

# The identity of a workflow worker, with the role that registers and runs
# workflows. Its API key or workload identity is added in the Admin Console.
resource "mistral_service_account" "worker" {
  workspace_id = local.workspace_id
  name         = "prod-worker"
  description  = "Runs the workflow workers of the production cluster."
  role_ids = [
    for r in data.mistral_assignable_service_account_roles.this.roles : r.id
    if r.name == "workflow_executor"
  ]
}
```

## Schema

### Required

- `name` (String) The name of the service account, unique in the workspace: a lowercase letter followed by lowercase letters, digits or hyphens, 2 to 63 characters, such as `prod-worker`. Changing it replaces the service account.
- `role_ids` (Set of String) The IDs of the workspace roles the service account holds, 1 to 14 of them. See the `mistral_assignable_service_account_roles` data source. A change replaces the roles as a whole.
- `workspace_id` (String) The ID of the workspace the service account belongs to: the workspace of the provider's API key. Changing it replaces the service account.

### Optional

- `description` (String) What the service account is for, up to 4096 characters.

### Read-Only

- `created_at` (String) When the service account was created, in RFC 3339 format.
- `id` (String) The service account ID, a UUID.
- `organization_id` (String) The ID of the organization of the workspace.
- `updated_at` (String) When the service account was last updated, in RFC 3339 format.

## Import

In Terraform 1.12 and later, an `import` block can use the resource identity:

```terraform
import {
  to = mistral_service_account.worker
  identity = {
    id = "8c2f4e1a-7b3d-4f6e-9a05-1d2c3b4a5f60"
  }
}
```
