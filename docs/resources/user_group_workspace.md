# mistral_user_group_workspace (Resource)

Gives the members of a user group access to a workspace, with the workspace roles they get there, with the Admin API key (`admin_api_key`). A member who joins the group later gets the roles too. The Admin API needs an Enterprise plan and access granted by Mistral.

-> **Public preview at Mistral.** The Admin API is in public preview: Mistral can change its fields without a deprecation period, and following them may take a new release of the provider.

~> **Not verified against the live API.** This resource is tested against a fake of the Mistral API written from Mistral's documentation. No acceptance test has run against a Mistral organization yet: please report any difference with the live API in an issue.

## Roles

`role_names` takes the workspace roles of the Admin API guide, such as `user` (Le Chat), `dev` (Studio and its primitives), `mistral_code_user`, `billing`, `workspace_contributor`, `workspace_admin` and `observability_viewer`, and the other names the API accepts. A change of roles updates the assignment in place. A member's roles in the workspace combine those of all their groups and those given to them directly.

The provider reads the roles back by their names. That they come back with the names it sent is our reading of the API reference, not a documented behaviour.

## Create and destroy

What the API does when the group already has access to the workspace is not documented. To avoid taking over an assignment made outside Terraform, the create fails in that case, and gives the `import` block that brings it under Terraform.

The API has no read of one assignment: every refresh lists the workspaces of the group, page by page, until it finds the workspace. Changing `group_id` or `workspace_id` replaces the assignment.

Destroying the resource removes the access of the group to the workspace. Its members keep the roles they hold there directly or through another group, and lose access when they have none left.

This resource suits a group that an identity provider syncs, read with the `mistral_user_group` data source: the identity provider keeps the membership, and Terraform keeps the access.

## Example Usage

```terraform
resource "mistral_user_group" "developers" {
  name = "Developers"
}

# Every member of the group can use Le Chat and Studio in the workspace.
resource "mistral_user_group_workspace" "developers_production" {
  group_id     = mistral_user_group.developers.id
  workspace_id = "5c6d7e8f-9a0b-4c1d-8e2f-3a4b5c6d7e8f"
  role_names   = ["user", "dev"]
}
```

## Schema

### Required

- `group_id` (String) The ID of the user group. Changing it replaces the assignment.
- `role_names` (Set of String) The workspace roles the members of the group get in the workspace, at least one, such as `user` (Le Chat), `dev` (Studio) or `workspace_admin`. A change updates the assignment in place.
- `workspace_id` (String) The ID of the workspace. Changing it replaces the assignment.

### Read-Only

- `id` (String) `<group_id>:<workspace_id>`.

## Import

In Terraform and OpenTofu 1.12 and later, an `import` block can use the resource identity:

```terraform
import {
  to = mistral_user_group_workspace.developers_production
  identity = {
    group_id     = "3f2b8c1e-5a4d-4e7f-9b6a-1c2d3e4f5a6b"
    workspace_id = "5c6d7e8f-9a0b-4c1d-8e2f-3a4b5c6d7e8f"
  }
}
```
